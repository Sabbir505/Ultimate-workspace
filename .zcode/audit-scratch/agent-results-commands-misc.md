## P0

**1. `set_chat_session_worktree` accepts any renderer-supplied path and permanently poisons the path-allowlist — arbitrary file read outside all project roots.**
- commands/worktree_cmds.rs:142-169 (persist at :167: `db::set_chat_session_worktree(&conn, &session_id, worktree_path.as_deref())`); db/chat.rs:270-280 is a bare `UPDATE chat_sessions SET worktree_path = ?2 WHERE id = ?1`.
Zero validation (not required to exist, be a git worktree, or sit under the owning project). That column feeds three gates that exist to stop a compromised webview: (a) `allowlisted_roots` (git_cmds.rs:72 `db::chat_worktree_paths(&conn, None)`) gates `read_file_text` (data.rs:496-499) and every git command; (b) `spawn_agent_session` uses it as the PTY cwd (pty_cmds.rs:78) for agent CLIs; (c) chat send paths resolve cwd the same way. The app's own comments define the adversary as a compromised renderer (data.rs:452-453 "prevents a compromised renderer from reading arbitrary files"; pty_cmds.rs:204), and `spawn_shell` runs an exec-gate dialog — but this one IPC call undoes the whole allowlist: invoke `set_chat_session_worktree(sessionId, "C:\\Users\\me")`, then `read_file_text` any text file ≤512KB under it (`.ssh/id_rsa`, `.env`, other apps' configs). Fix: canonicalize `worktree_path`, require an existing directory under the session's project root (ideally confirmed via `git worktree list` from that root); reject everything else. Mirror in the stale-pointer re-create path.

## P1

**2. `browser_confirm_result` has no nonce — a hostile page can self-approve its own risk gate (same spoof class fixed as M-11).**
- commands/browser_cmds.rs:253-264 → browser/tabs.rs:195-198 `gate_request_resolve(req_id, ...)`; gate ids from `next_gate_req: AtomicU64` starting at 1 (browser.rs:2021, 2061) — sequential, guessable.
The sibling command's comment (browser_cmds.rs:126-131) states the threat: "pages in a pane can reach this command via the injected JS's Tauri invoke fallback — the old `None` arm resolved unverified, so a hostile page could spoof any in-flight action's result (audit M-11)" — which is why `browser_action_result` now requires a nonce. `browser_confirm_result` never got the fix: a hostile page the agent operates on can invoke `browser_confirm_result(req_id, approved=true, always_for_site=true)` (spamming a small id range; only pending ids resolve) and defeat the consent layer for risky agentic actions. Same unverified pattern in `browser_resolve_pane_result`/`browser_open_pane_result`/`browser_tab_result` (228-246, 313-320, lower impact). Fix: per-request random nonce on the `browser:confirm-request` payload, verified inside `gate_request_resolve`; same for pane/tab roundtrips.

**3. Singular `kind` strings break every installed-skill disk operation in the artifact flows (create errors after writing files; update errors after the DB write; filesystem-only skills uneditable).**
- commands/artifact_cmds.rs:147-151, 420, 444, 477, 523-525.
`installed_skills::roots(kind)` (installed_skills.rs:104-110) uses the kind verbatim as the dir segment (`~/.claude/<kind>`), so only "skills"/"loops" scan real dirs; `skills_cmds::kind_key` (121-126) normalizes singular→plural but only the create path goes through it. The adapter produces singular kinds (artifacts/adapter.rs:54 `adapt_skill(s, "skill")`, :103 `kind: "loop"`). Consequences: (a) create — `save_installed(&installed.slug, &input.kind, ...)` (147-151) scans `~/.claude/skill`, misses, errors AFTER `create_installed_skill` wrote both harness copies — `create_artifact_cmd` fails for every Skill/Loop artifact; (b) update — `read_installed(&artifact_id, artifact_type.as_str()).is_some()` (420) always false, so filesystem-only skills always hit `Err("Artifact {} not found")` (421-423) and rename stale-slug cleanup (433-441) is dead code; (c) deferred write `save_installed(&slug, &kind, ...)` (523-525, kind = "skill"/"loop") errors after `update_skill` committed the DB row — every skill/loop/prompt-template edit returns Err with a confusing message and leaves the harness twin stale. Fix: normalize the kind at the `installed_skills` API boundary (accept both forms via `kind_key`, or export `kind_key` and use it at every artifact-flow call site).

**4. `update_skill`'s harness-twin mirror silently never runs (same singular-kind bug, errors swallowed with `let _`).**
- commands/data.rs:293-296: `let _ = save_installed(&slug, "skill", &content);` / `let _ = delete_installed(&old_slug, "skill");` — `"skill"` scans `~/.claude/skill`, which doesn't exist, so both always fail, discarded. The comment (286-290) says the mirror exists so the twin doesn't "keep serving the stale body/slug" — in practice editing or renaming a DB skill in the Skills UI leaves the installed harness slash-command copy permanently stale, and a renamed skill's old twin stays installed as a live duplicate command. Fix: pass "skills" (reuse `kind_key`), surface the failure.
